## 2. QW-2 — Claim → Topic File Pipeline

### 2.1 Routing (Inference Pass)

Para cada claim no SSOT:

1. Se `topic_id` está preenchido → usa directamente
2. Se `topic_id` é null → inference pass:
   - Extrai tags/nome do `source_ref` (TLDV meeting name, GitHub repo, Trello board)
   - Usa regex/tag-matching para mapear para topic file
   - Pattern matching (case-insensitive):
     - `bat`, `kaba`, `bot` → `bat-conectabot-observability.md`
     - `tldv`, `memory`, `livy`, `openclaw`, `gateway` → `livy-memory-agent.md`
     - `delphos`, `vistoria` → `delphos-video-vistoria.md`
     - `forge` → `forge-platform.md`
     - `evo`, `evolution` → `livy-evo.md`
   - Se nenhum match → fallback para `general.md` (ou skipped com warning)

**Pipeline popula `topic_id`:** Quando uma claim passa pelo inference pass e é escrita num topic file, o SSOT é actualizado com o `topic_id` resolvido. Próximos runs usam directamente.

### 2.2 Fact Checking (antes de escrever)

Para cada candidate claim:

| Check | Obrigatório | Acção se fail |
|---|---|---|
| **A. Dedupe textual** | ✅ | Skip — já existe no topic file (similarity >0.85 via SequenceMatcher) |
| **B. Supersession check** | ✅ | Skip — claim tem `superseded_by` activo |
| **C. Evidence existence** | ⚠️ Warning | Log warning; não bloqueia write |

### 2.3 Schema Validation

Para cada claim lida do SSOT:

| Campo | Obrigatório | Validação |
|---|---|---|
| `claim_id` | ✅ | string não-vazia |
| `claim_type` | ✅ | enum: `decision`, `linkage`, `status`, `timeline_event` |
| `text` | ✅ | string não-vazia |
| `source` | ✅ | string não-vazia |
| `confidence` | ✅ | float 0.0–1.0 |
| `topic_id` | ⚠️ | null aceite; se presente, deve ser string |
| **PII check** | ⚠️ Warning | Se `text` contém patterns suspeitos (emails, tokens, URLs externas) → log warning, não bloqueia |

### 2.4 SSOT Query Strategy

Mantém cursor por source em `.research/qw2/last_seen_<source>.json`:

```json
{
  "tldv": "2026-05-23T10:00:00Z",
  "github": "2026-05-23T10:00:00Z",
  "trello": "2026-05-23T10:00:00Z"
}
```

- Lê só claims onde `ingested_at` > cursor dessa source
- Actualiza cursor após processar cada source
- Mantém `processed_decision_keys` e `processed_linkage_keys` como secondary dedupe gate

### 2.5 Write Strategy — Approve-then-Write

**QW-2 NUNCA escreve directamente nos topic files.**

Fluxo:

1. Claim passa fact-check + schema validation
2. QW-2 determina routing (DM ou grupo) — ver 3.1
3. Escreve ficheiro em `memory/vault/pending/<claim_id>.json`:
   ```json
   {
     "claim_id": "...",
     "claim_type": "decision",
     "text": "...",
     "topic_file": "bat-conectabot-observability.md",
     "source": "tldv",
     "confidence": 0.87,
     "needs_review": false,
     "routing": "dm",
     "created_at": "2026-05-23T...",
     "warnings": []
   }
   ```
4. **Event-triggered:** QW-3 é invocado via cron ou signal
5. Lincoln aprova → QW-3 escreve no topic file e marca pending como `approved`
6. Lincoln rejeita → QW-3 arquiva em `memory/vault/pending/archive/<claim_id>.json`

## 3. QW-3 — Revisão Humana

### 3.1 Routing — DM vs Grupo

| Condição | Destino |
|---|---|
| `needs_review == true` | DM (7426291192) |
| `claim_type == "decision"` AND `confidence < 0.85` | DM |
| `claim_type == "linkage"` | Grupo (silent) |
| `claim_type == "status"` | Grupo (silent) |

### 3.2 DM — Formato e Interacção

**Mensagem:** Texto curto com:
- Claim type + source
- `confidence: X%`
- `text` da claim
- 3 botões inline:
  - ✅ **Aprovar** → `approve:<claim_id>`
  - ❌ **Rejeitar** → `reject:<claim_id>`
  - ⏭️ **Skip** → `skip:<claim_id>`

### 3.3 Grupo — Overview HTML

Accionado quando:
- QW-2 escreveu ≥1 pending items
- Ou weekly (segunda 07h) se não houve notificação

**Formato:** HTML auto-contido (CSS inline), estilo Delphos/BAT reports:
- Tabela com: Date | Source | Topic | Claim type | Confidence | Text (truncated)
- Footer com timestamp do report
- Sem botões de acção (só visualização)

**Delivery:** `sendDocument` ao grupo `-5158607302` via `@livy_agentic_memory_bot`

### 3.4 Schedule

| Gatilho | Acção |
|---|---|
| QW-2 escreve pending item | Cron invocado; processa todos os pending |
| QW-2 não escreveu e é segunda 07h | Overview weekly ao grupo (se há items) |

Cron: `qw3-review` — event-triggered via internal queue.

## 4. Mitigação de Riscos

### Risco A: Topic File Corruption
- **Mitigação:** Backup automático antes de qualquer write (padrão existente em `research_guardrails_cron.py`)
- Backup path: `memory/curated/.backups/<topic_file>.<timestamp>.bak`
- Validação post-write: ler topic file e verificar que claim aparece

### Risco B: Pending Accumulation
- **Mitigação:**
  - TTL: claims em pending > 30 dias sem acção → auto-archive
  - Max size: > 100 pending items → pausa QW-2 e alerta
  - Alerta a 80% (80 pending): notificação a Lincoln

### Risco C: False Positives no Fact-Check
- **Mitigação:**
  - Threshold 0.85 (não 0.70) para dedupe fuzzy
  - False positive dispute: Lincoln pode marcar `manual-override` num claim
  - QW-2 depois ignora dedupe para claims com `manual-override: true`

### Risco D: Claim Loss on Reject
- **Mitigação:**
  - Reject move para `archive/<claim_id>.json` (não delete)
  - Backup in-place antes de marcar reject (mesmo padrão de approval)
  - Log em `vault/logs/qw3_rejections.jsonl`

### Risco E: Spam pelo Bot
- **Mitigação:**
  - DM: máx 1 por semana por source (a menos que > 5 pending items)
  - Grupo: máx 1 overview por semana (segunda)
  - Se QW-2 acumulou < 3 pending items → silencioso (sem DM)
